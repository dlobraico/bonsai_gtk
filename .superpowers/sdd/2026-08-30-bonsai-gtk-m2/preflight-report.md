## Extra assumptions

**(a) Synthetic key press / click delivery — plan needs correction, see below.** Findings from the pinned checkout:
- No `gtk_test_*` binding exists anywhere (`ls .ocgtk-src/.../gtk/generated | grep -i test` → empty; confirmed again with a broader `grep -rln gtk_test_` → empty).
- **No `GdkEvent` constructor exists for any event subtype** — checked every `*event*.mli` under `gdk/generated/` for `new_`/`alloc`/a constructor: none. A synthetic `GdkEvent` cannot be built from OCaml through this binding at all.
- `Gobject.Signal.emit_by_name : 'a obj -> name:string -> unit` and `.notify : 'a obj -> name:string -> unit` both exist but take **no arguments** — neither can carry a click's `~button ~n_press ~x ~y` or a key-press's `~keyval ~keycode ~state`.
- `Event_controller_key.forward : t -> Widget.t -> bool` exists, but its doc says it "can only be used in handlers for … `key-pressed`, `key-released` or `modifiers`" — it **re-routes an event a controller is already processing**; it does not originate one. It is not usable to synthesize an initial key-press for a live test starting from nothing.
- `Widget.grab_focus : t -> bool`, `Widget.mnemonic_activate : t -> bool -> bool`, `Widget.activate_default : t -> unit`, and `Widget.activate_action_variant : t -> string -> Gvariant.t option -> bool` all exist. Per `grab_focus`'s doc, it is a real focus-chain operation and should genuinely drive `EventControllerFocus`'s `on_enter`/`on_leave` — but only on a realized/mapped widget.
- **New finding not in the plan's fact table:** `Widget.observe_controllers : t -> Gio.Wrappers.List_model.t` exists (found twice in the generated `.mli`, once per widget-cycle file) — a live `GListModel` tracking the widget's attached controllers. This makes the plan's fallback option (c) concrete: a live test can assert "adding the attr attaches a controller" and "removing it detaches" by checking this list model's item count, not merely "the widget didn't crash."

**Conclusion:** click and key-press cannot be genuinely simulated at the GTK/GDK level with this binding — no event constructor, no argument-carrying emission, and `forward` requires a real event already in flight. The plan's own stated fallback (attach/detach/survive via plumbing, handler logic tested headlessly through `Bonsai_gtk_test`) is not just the fallback — for click and key-press it is the *only* option, now strengthenable with `observe_controllers`. Only the **focus** controller has a real, working simulation path (`grab_focus`), and only once the widget is actually shown/presented.

## Corrections the plan needs, most consequential first

1. **Task 5's claim that a key press "is deliverable" via `Event_controller_key.forward` overstates what `forward` does.** `forward` only re-routes an event a controller is *already* handling; it cannot originate a synthetic key-press, and no `GdkEvent` constructor exists anywhere in the binding to make one from scratch. The task text (around plan line 1753) should be corrected before an implementer spends time trying to build a live key-press test around `forward` and discovers mid-task that it never fires without a pre-existing real event. The actual answer to "check whether a GdkEvent can be synthesised from the binding" is **no** — the plan should say so plainly rather than leave it as an open question, and commit up front to the plumbing-only live test (attach/detach via `observe_controllers`) plus headless handler tests via `Bonsai_gtk_test`, for *both* click and key-press controllers.

2. **Task 4's `live_controllers.ml` sample code never shows/presents the window** (`on_window_created:(fun _ -> ())` is a no-op), so even the one mechanism that can be genuinely tested live — focus, via `Widget.grab_focus` — will not fire real `enter`/`leave` signals as written, since `grab_focus` needs a realized/mapped widget. This needs a `Widget.show` or equivalent presentation call added before the focus assertions, or the "what is certainly testable" focus test will silently produce `false`/nothing instead of the expected trace.

3. **`Widget.observe_controllers` should be named explicitly in Task 4's "Consumes:" list** and used to make the attach/detach assertion concrete (assert the list model's item count goes N → N+1 → N) rather than the current "the widget is still alive and patchable" proxy, which is weaker than what the binding actually supports.

4. **Task 2's Step 5 (`batch_if`) should not be skipped as "the cost is free"** — it measurably isn't (≈79.5 ns/call, 100k calls = 7.95 ms on a real `GtkLabel`). It's cheap enough that skipping it would cost little, but the plan's exact escape-hatch condition ("if `freeze_notify`/`thaw_notify` on an unchanged object is already free") is not met, so the task report should record the actual numbers rather than round down to "free."

Everything else on the checklist (items 1–3, 6, 7, 9–12) and extra assumptions (b) and (c) matched the plan exactly; no rework needed there.
