## Summary

The suite is in good shape and its instruments are real. Six targeted mutations of
assertions the milestone leans on were all caught, one of them by a segfault-equivalent
and one by the compiler; the ratio benches are sharp instruments (the flow-box mutation
moves the ratio from 1.1 to 51 against a bound of 5). There are **no `sleep`s anywhere in
`test/live/`** — the one wait, `live_controls.ml`'s `pump_for`, is expiry-ordered rather
than racy and holds at any load. The determinism story is better than the ledger claims.

Three things stand between the branch and a merge, and two of them are in `scripts/ci.sh`
rather than in the tests:

1. **`ci.sh` does not neutralise an inherited `BONSAI_GTK_LIVE_TESTS`.** When it leaks in,
   three earlier sections run the live suite unserialised and without `xvfb`, and the
   section that carries the `-j 1` fix then finds everything up to date and runs nothing.
   Proven end to end. This is a false *green*, and it silently deletes the milestone's
   headline determinism fix.
2. **`live_embed.ml`'s `bound_ratio = 1.2` is the one remaining bound that flakes at 2x
   oversubscription** — 3 failures in 30 standalone runs, and it failed inside the real
   alias run twice during this review. It is not the display race: neither `-j 1` nor
   `(locks)` fixes it.
3. **A second `ci.sh` in the same tree does not re-run the live suite at all** (4 s, zero
   bench lines). The ledger files this trap against `--force` only; it applies to the
   plain gate command, and because the bench rules are not pure functions of their
   deps, dune caches a lucky green while re-running every red.

On the parked question: **`(locks x-display)` should replace `-j 1` in the fix wave.**
Measured, it costs 1 s where `-j 1` costs 26 s on a cold tree, it is equally effective
against the focus race (0 failures in 6 loaded runs vs 4 in 7 unserialised), and — the
argument the timings do not carry — it binds the constraint to the rules, so `dune test`,
an editor's run-tests action, and finding (1) above all inherit it. Numbers in
"§ `(locks)` vs `-j 1`" below.

On the XTEST bead: the backlog names two blockers, and **one of them is already solved** —
`Widget.compute_bounds`, `compute_point` and `translate_coordinates` are all bound in the
pinned ocgtk, so widget-to-coordinate mapping needs no fork patch. Concrete sketch below.

## Critical

### C1 — `scripts/ci.sh` leaks `BONSAI_GTK_LIVE_TESTS`, and the leak makes the live section vacuous

`scripts/ci.sh:1-6` sets no value for `BONSAI_GTK_LIVE_TESTS`; only `scripts/ci.sh:88`
sets it, inline, on the one line that wants it. Nothing else in the script, in
`scripts/setup-switch.sh`, or in `flake.nix` mentions the variable. So a developer who has
`export BONSAI_GTK_LIVE_TESTS=1` in their shell (which is exactly the developer who has
been running live tests by hand — the `test/live/dune` header tells them to type it)
changes what three earlier sections do:

- `scripts/ci.sh:56` `dune build @test/runtest` — the alias is recursive, so it reaches
  `test/live/runtest`;
- `scripts/ci.sh:66` `dune build --build-dir=_build.pkg -p bonsai_gtk @runtest` — verified
  to reach the live rules too (the `executables`/`rule` stanzas in `test/live/dune` name no
  package, so `--only-packages` does not filter them out);
- and `scripts/ci.sh:70` for the same reason.

Failure scenario, verified in full:

```
$ export BONSAI_GTK_LIVE_TESTS=1
# step A — ci.sh's "== pure + headless tests" line, with a display available
$ xvfb-run -a dune build @test/runtest
  … all eleven live suites run, in parallel, on one display …
  exit=0  elapsed=68s   live outputs now present: 11
# step B — ci.sh's "== live tests (xvfb)" line, immediately after
$ BONSAI_GTK_LIVE_TESTS=1 xvfb-run -a dune build @test/live/runtest -j 1
  bench lines printed: 0
  elapsed=3s
```

Step A is precisely the shape `-j 1` exists to prevent — eleven toplevels mapping on one
shared display — and step B, the line that carries the fix, runs nothing because step A
already produced the targets. On a host with no `DISPLAY` the same leak instead aborts the
gate at step A with `Ocgtk_gtk__GMain.Error("GTK initialization failed")` reported under
the heading "pure + headless tests" (also verified, exit 141). On a developer's desktop
with a real X session it is worse than either: eleven windows open on their session, the
focus block flakes for the documented reason, and the diff reads as a regression in the
focus controller.

Severity: this is a false green on the merge gate that removes the milestone's headline
determinism fix without any visible sign. Fix is one line after the `cd` at
`scripts/ci.sh:5`:

```bash
# The live rules are enabled by this variable and must run only under the xvfb line
# below, one at a time. Neutralise whatever the caller's shell had.
export BONSAI_GTK_LIVE_TESTS=0
```

`(locks x-display)` (see below) independently defangs the *serialisation* half of this,
which is a second reason to prefer it; the export is still wanted, because a live suite
running inside the "pure + headless tests" step is wrong whether or not it is serialised.

### C2 — `live_embed.ml`'s `bound_ratio = 1.2` flakes at 2x oversubscription

`test/live/live_embed.ml:556`. This is the one wall-clock-derived bound in the suite that
fails under load. Measured:

| condition | runs | failures | ratios observed |
|---|---|---|---|
| idle host, `live_embed.exe` alone | 10 | 0 | 0.84 – 0.93 |
| 2x oversubscription, `live_embed.exe` alone | 30 | **3** | 0.45 – **1.23** (fails at 1.21, 1.23, 1.23) |
| 2x oversubscription, inside `@test/live/runtest` | — | 2 observed | 1.27 and one more |

Two of those alias-level failures happened during this review's other experiments, so they
are not synthetic: one appeared in the unserialised race batch (`output_embed.txt`,
ratio 1.27) and one in the `(locks)` batch — i.e. this survives both proposed
serialisations, because it is not the display race.

The cause is in the comment that defends the bound (`live_embed.ml:532`): *"contention
scales both measurements and cancels"*. That holds for the four benches with `bound_ratio
= 5.0`, and it does not hold here, for two compounding reasons.

- The two measurements are taken **sequentially**, windowed first (`:574`) then embedded
  (`:579`), so contention cancels only to the extent that load is stationary across the
  two phases. It is not.
- Each phase is `2000` frames at ~9 µs, i.e. **~18 ms of wall clock**. That is a short
  enough window for one descheduling event or one major GC slice to move a phase by tens
  of percent, and the bound leaves only 35% of headroom over the measured 0.87.

The other four benches survive the same load: `live_lists` at bound 5.0 was 0/6 with a
worst observed ratio of 2.43, and the `live_text` pair never left 0.5–1.3.

Any one of three fixes works, in increasing order of quality:

1. Raise `bound_ratio` to `2.0`. The comment's own stated claim — "1.2 still catches a
   doubling" — is still true at 2.0 for a doubling, and 2.0 is clear of every sample I
   took under load. One character.
2. Interleave the phases: run windowed and embedded frames alternately inside one loop and
   accumulate two totals. Then contention really does cancel, which is what the comment
   asserts, and the bound can stay at 1.2.
3. Raise `frames` so each phase is ≥ 1 s of wall clock (about 100 000 frames), which
   averages the noise out. Costs a second of gate time.

(2) is the one that makes the existing comment true; (1) is the one that ships today.
Either way the comment at `:532` needs a sentence saying that the cancellation argument
requires the measurements to be concurrent, not merely both present.

## Important

### I1 — a second `ci.sh` in the same tree does not run the live suite

Verified in the real tree, immediately after a green `ci.sh`:

```
$ BONSAI_GTK_LIVE_TESTS=1 xvfb-run -a dune build @test/live/runtest -j 1
bench lines printed: 0
elapsed: 4 s      (a real run takes ~29 s and prints 8 bench lines to stderr)
```

The ledger and `scripts/ci.sh:78-81` record this trap, but only against `dune build …
--force` and only as advice for anyone re-measuring the flake. It applies to the gate
command itself: `nix develop -c ./scripts/ci.sh` twice in a row exercises the live suite
once. Task 16's protocol was clean-tree runs, so it never met this.

It is not a soundness bug in dune's sense — the rules' declared deps are complete, and if
nothing the executables depend on changed, the old result is still the result. What makes
it worth fixing is that **these particular rules are not pure functions of their deps**:
five of them assert on wall-clock ratios. So the caching is asymmetric in the wrong
direction — a run that got lucky is cached green until an executable changes, while a red
is re-run every time. That is also why "just run it again and see if it reproduces" is
currently a no-op, which is the exact investigation C2 will provoke.

One line before `scripts/ci.sh:88`:

```bash
# These rules declare targets, so dune will not re-run them for an unchanged tree --
# and their goldens include wall-clock ratios, which are not a function of the deps.
rm -f _build/default/test/live/output_*.txt
```

### I2 — the selection bench guards `w_flow_box` only; `w_list_box`'s identical copy is unguarded

`test/live/live_lists.ml:1694` builds the bench tree from `Node.flow_box`. That is the
only container the cost regression at `:1695-1760` ever measures, and the property it is
defending is implemented twice: `src/widgets/w_flow_box.ml:212-235` and
`src/widgets/w_list_box.ml:229-251` are the same per-call key table, added by the same
task for the same reason (`task-7-review.md` I1).

Verified by mutation, three ways:

| mutation | result |
|---|---|
| `w_flow_box.ml`: `Hashtbl.{mem,find} by_key` → `child_by_key w` (the shipped-then-fixed quadratic shape) | **caught** — golden flips, `ratio 51.02 (bound 5)` |
| `w_list_box.ml`: the identical change, `Hashtbl.{mem,find} by_key` → `row_by_key w` | **not caught** — `expected_lists.txt` byte-identical, measured ratio 1.12 vs 1.10 baseline |
| `w_list_box.ml`: `apply_selection` made a no-op (control, to prove the file is reached) | caught immediately — `gc: mounted, selected (none)`, and the `Live_tree` dump loses `(selected-rows 2)` |

So list-box selection *correctness* is well covered and its *cost* is not covered at all.
The reason this matters more than a usual coverage gap: `docs/m2-backlog.md:128` already
records that `w_list_box.ml` and `w_flow_box.ml` are two copies of one container which M2
declined to merge. Two copies with one regression test between them is how the copies
drift. The fix is a few lines — parameterise `idle_frame_ms` over the container node and
call it twice, or add a second bench block over `Node.list_box`.

### I3 — `eval "$(opam env …)"` at `scripts/ci.sh:6` cannot fail the script

Verified:

```
$ bash -c 'set -euo pipefail; eval "$(opam env --switch=/nonexistent --set-switch 2>/dev/null)"; echo "SURVIVED, exit=$?"'
SURVIVED the failed opam env, exit=0
```

`set -e` does not fire on a command substitution used as an argument to `eval`, and
`eval ""` succeeds. If the local switch is missing or broken, `ci.sh` continues against
whatever OCaml and dune happen to be on `PATH` inside the dev shell. Usually that fails
confusingly two lines later; the case worth guarding is a *usable but different* switch,
where the gate silently certifies against the wrong dependency set. Two lines:

```bash
opam_env=$(opam env --switch=. --set-switch)   # fails the script if the switch is not there
eval "$opam_env"
```

## Determinism sweep — what is clean

Recorded because "no findings" here is itself a result, and because it narrows what the
fix wave has to think about.

- **No `sleep`, `nanosleep`, `Unix.sleep` or busy-wait-on-the-clock anywhere in
  `test/live/`.** Grepped every file for the whole family.
- **The one wait is not a race.** `test/live/live_controls.ml:26` `pump_for ~ms` arms a
  GLib timeout and blocks in `Glib.Main.iteration true` until it fires. It is used three
  times at `~ms:60` against a `~search_delay:10` debounce (`:494`). GLib dispatches
  timeouts in expiry order, and the debounce is always armed *before* the pump's own
  timeout, so the 10 ms source is always dispatched first no matter how loaded the host
  is. The negative assertions ("0 searches after the mount wrote the text") only get
  stronger with delay. This one is genuinely load-independent, and the comment at `:20-25`
  is accurate.
- **The only wall-clock assertions in the suite are the five bench ratios.** Four are at
  `bound_ratio = 5.0` and were clear under 2x oversubscription (worst observed: `live_lists`
  2.43, `live_text` 1.27). The fifth is C2.
- **No dependence on locale, `TZ`, hostname, `Random`, or any environment variable other
  than `BONSAI_GTK_LIVE_TESTS`.** The single `Date.today` (`live_text.ml:1802`) and the
  unbounded `Glib.Main.pending` drains (`live_driver.ml:26`, `live_lists.ml:165`) are both
  already on `docs/m2-backlog.md`; not re-reported.
- **`live_keyvals.ml` is a pure constant comparison** against `Ocgtk_gdk.Gdk_constants` —
  no display, no layout, no XKB. It cannot flake.

Invocations that still map a toplevel outside the serialised alias, for completeness:
`dune test` / `dune build @runtest` at the root, `dune build @test/runtest`,
`dune build @test/live/runtest` without `-j 1`, any editor "run tests" action, and — the
one that matters, because it happens inside the gate — C1. Every one of them is fixed by
`(locks x-display)` and none of them by `-j 1`. `dune build @all` is safe: the live rules
attach to `runtest` only.

## `(locks x-display)` vs `-j 1` — the recommendation

**Recommendation: swap `-j 1` for `(locks x-display)` on the nine rules that present a
toplevel, in the fix wave.** It is equally effective, it is 25 s cheaper on a cold tree,
and — the part the timings do not show — it fixes C1's serialisation half and every
`dune test` / editor invocation, which a flag on one call site cannot.

I prototyped it: `(locks x-display)` added to all eleven rules in `test/live/dune` in the
throwaway worktree. All measurements are `BONSAI_GTK_LIVE_TESTS=1 xvfb-run -a dune build
@test/live/runtest`, "warm" = executables built and `output_*.txt` deleted, "cold" =
`rm -rf _build/default/test/live` (so eleven executables are recompiled and relinked).

**Cost**

| | warm | cold |
|---|---|---|
| `-j 1` (shipped) | 31 s | **59 s** |
| no serialisation | 28 s | 32 s |
| `(locks x-display)`, default `-j` | 31 s | **33 s** |

Warm, they are indistinguishable and both cost the ~2-3 s over unserialised that
`scripts/ci.sh:83` already documents. Cold, `-j 1` costs **26 s** and `(locks)` costs
**1 s**, because `(locks)` serialises only the rule *actions* while the eleven compiles and
links still run in parallel. Inside `ci.sh` the tree is always warm (`dune build @all`
precedes), so this is not a gate-time argument — it is an argument about every developer
who types the command out of `test/live/dune`'s header on a tree that is not warm, which
is the situation the header's own caveat at `:29-34` was written for. `(locks)` deletes
that caveat instead of documenting it.

**Effectiveness** — 2x oversubscription throughout, warm tree, full alias each run:

| arrangement | runs | failures | which rule |
|---|---|---|---|
| no serialisation | 7 | **4** | ≥3 × `output_controllers.txt` (the focus block), 1 × `output_embed.txt` |
| `(locks x-display)`, default `-j` | 6 | 1 | `output_embed.txt` only — **zero focus failures** |
| `-j 1` | 3 | 0 | — |

The unserialised number (4 in 7) sits on top of the previous reviewer's 3 in 7 and the
ledger's 1 in 10, so the race is easy to reproduce here. `(locks)` removed it completely,
and its single failure was C2's embed bench, which no serialisation can fix. The `-j 1`
sample is small (3 runs) because each takes ~80 s under load; it is consistent with the
ledger's 0 in 15 and 8 in 8.

**The argument the numbers do not carry.** `-j 1` is a property of one invocation in one
script. `(locks)` is a property of the rules, so it is inherited by
`dune build @test/live/runtest` with no flags, by `dune test`, by an editor's run-tests
action, and — critically — by the leaked-environment path in C1, where `dune build
@test/runtest` currently runs all eleven at once. Task 16's review already recorded
`(locks)` as "verified as the better mechanism" and left the decision here; the cold-tree
number and C1 are the two things that were not on the table then, and both point the same
way.

**What the change is.** Add `(locks x-display)` to the nine rules whose executable calls
`GMain.init`; leave it off `live_events` and `live_keyvals` (M1). Then delete `-j 1` from
`scripts/ci.sh:88` and rewrite the comment block at `:78-86` and `test/live/dune:18-34`
to describe the lock. Eleven — nine — small edits with no behavioural risk: dune's `locks`
is a documented mutual-exclusion primitive, the rules already declare their targets, and
the fallback if it ever misbehaves is the flag that is there today.

## The XTEST bead — what a re-runnable version needs

`docs/m2-backlog.md:373-395` calls this the single most valuable follow-up and names two
unsolved problems. **One of them is already solved in the pinned binding**, which changes
the cost estimate materially.

**Already available.** `Widget.compute_bounds`, `Widget.compute_point` and
`Widget.translate_coordinates` are all bound in the pin (verified in
`_opam/lib/ocgtk/gtk/generated/event_controller_and__layout_child_and__layout_manager_and__root_and__widget.mli:207,1503,1531`).
So "mapping a widget to screen coordinates" — the problem the by-hand run solved by
reading pixels off a screenshot, and the one that made a 14 px miss look like a broken
handler — needs **no fork patch and no new binding**. The backlog's framing should be
corrected.

**What is actually missing.**

1. **`xdotool` is not in the dev shell.** `task-16-clickthrough/clickthrough.sh:9` works
   around this with a hardcoded absolute store path
   (`/nix/store/rvhy0…-xdotool-3.20211022.1/bin`). That path is alive today — I checked —
   but it is not a GC root, so the script is one `nix-collect-garbage` away from failing,
   and it fails *misleadingly*: `xdotool search` is guarded by `|| true` at `:21`, so a
   missing binary surfaces as `no window` at `:26`. Fix: add `xdotool` to the devShell in
   `flake.nix` and delete the `PATH` line. ImageMagick is needed only for the human-facing
   screenshots, not for a test.
2. **Nineteen `sleep`s** across the two scripts (11 + 8), which is what makes it a
   demonstration rather than a test.
3. **Hardcoded pixel coordinates** read off screenshots (`mousemove 36 288`,
   `680 146`, …), which is the same problem as (1) in a different costume: they encode one
   window size and one theme.

**The shape a test should take.** Not a shell driver against `examples/gallery.exe` — a
twelfth live executable, `test/live/live_input.ml`, which is both the application and the
driver. That removes every one of the three problems at once:

- It builds a small tree of its own (a button with `Attr.on_click`, an entry under a
  `Capture`-phase `Attr.on_key_pressed`), presents it, and drains the loop until mapped.
- It computes its own target coordinates with `Widget.compute_bounds` on the target widget
  relative to the toplevel — the toplevel is at (0,0) under Xvfb with no window manager,
  which Task 16 established — so no screenshot and no hardcoded pixel is involved, and the
  test *cannot* silently click into margin space the way the by-hand run did.
- It spawns `xdotool` with `Unix.create_process` (`windowfocus` on its own window found by
  a unique title, then `mousemove … click N` / `key`), and then **pumps its own main loop
  until the handler's counter moves, bounded by an iteration count** — exactly the pattern
  `live_embed.ml:23-27`'s bounded `drain` already uses. That is the "settling wait that is
  not a `sleep`" the backlog asks for, and it is the reason this has to be one process
  rather than a script plus a GUI.
- It prints the `Click_event.t` / `Key_response.t` readouts and diffs against a golden,
  like every other rule in the directory.
- Its dune rule carries `(locks x-display)` and the existing `enabled_if` on
  `BONSAI_GTK_LIVE_TESTS`, plus a second `enabled_if` clause or a `(deps %{bin:xdotool})`
  so it is skipped rather than red where `xdotool` is absent.

Note the one thing that must be XTEST and not `XSendEvent`: GTK ignores `send_event`
records by default, so `xdotool key --window $WID` will not work and `windowfocus` + plain
`key` (which is XTEST) will — Task 16 found this empirically and it should be written down
in the test, because it is the first thing someone will try to "simplify" to.

**For the merge decision.** This is a bead's worth of work (a day, not an hour) and it
closes the milestone's only genuinely uncovered claim — that GTK routes a real button
press and a real keystroke to the controller this library attached, and that key
propagation works. It does not block the merge: the compensating controls (plumbing in
`live_controllers.ml`, handler in `test_handle.ml`, trampoline in `live_signals.ml`, the
gallery Input page) are real and the gap is honestly documented. But the estimate in the
backlog is now too pessimistic by whatever a fork round costs, and the bead text should be
updated to say so.
